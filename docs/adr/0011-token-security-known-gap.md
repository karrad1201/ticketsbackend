# ADR 0011: Known Security Gap — Bearer Token без Device Binding и Revocation

## Status

Accepted (deferred)

## Context

Текущая схема аутентификации:

1. Пользователь верифицирует телефон через SMS-код.
2. Бэкенд выдаёт единственный долгоживущий Bearer-токен.
3. Клиент хранит токен в памяти процесса (`AppSession.authToken`).
4. Каждый запрос содержит `Authorization: Bearer <token>` и `X-User-Id: <uuid>`.

Токен не привязан к:
- конкретному устройству (нет device fingerprint, нет push challenge)
- IP-адресу или географии
- сессии с возможностью отзыва

Нет механизма rotation: токен действует до истечения срока, отозвать его точечно нельзя.

### Вектор атаки

Злоумышленник с **физическим доступом к разблокированному устройству**:

1. Читает токен из памяти процесса (root-доступ, ADB backup, либо уязвимость конкретной версии ОС).
2. Использует токен с произвольного устройства / IP без каких-либо дополнительных проверок.
3. Жертва не получает уведомлений, не может завершить сессию удалённо.
4. Атака работает до истечения токена — без rotation это может быть неограниченно долго.

### Почему это не критично прямо сейчас

- Нет prod-деплоя с реальными пользователями и деньгами.
- Сам по себе физический доступ к разблокированному телефону уже означает компрометацию
  большинства приложений — это проблема модели угроз уровня устройства, не только нашего токена.
- Реализация полноценного решения требует нетривиальной инфраструктуры (Redis session store,
  device registration, push notification challenge), что сдвигает другие приоритеты.

## Decision

Зафиксировать gap как известный, не решать сейчас.

Когда придёт очередь — реализовать следующее:

### Шаг 1: Short-lived access token + refresh token rotation

- Access token: 15 минут.
- Refresh token: 7–30 дней, хранится в Redis с возможностью точечного удаления.
- При каждом refresh — старый refresh token инвалидируется, выдаётся новый (rotation).
- Обнаружение reuse refresh token → инвалидация всей семьи токенов (признак кражи).

### Шаг 2: Session registry

- Каждая сессия имеет `sessionId`, `deviceHint` (user-agent + платформа), `createdAt`, `lastUsedAt`.
- Пользователь видит список активных сессий и может завершить любую.
- Администратор может завершить все сессии пользователя принудительно.

### Шаг 3: Anomaly detection (опционально)

- При использовании refresh token с нового IP / страны — push-challenge или повторная SMS-верификация.
- Логирование подозрительных событий.

## Consequences

До реализации:

- Физический доступ к устройству = неограниченный доступ к аккаунту.
- Нет способа завершить сессию удалённо.
- Компрометация токена обнаруживается только случайно (подозрительные действия в аккаунте).

После реализации Шага 1:

- Окно атаки сужается до 15 минут (access token TTL).
- Кража refresh token обнаруживается при его повторном использовании.

После реализации Шага 2:

- Пользователь может самостоятельно закрыть скомпрометированную сессию.
