# ADR 0002: Materialize Organization on Application Approval

## Status

Accepted

## Context

После первого среза `Organization` следующая бизнес-точка входа по продуктового флоу:

- пользователь существует;
- пользователь подает заявку на организацию;
- админ рассматривает заявку;
- при аппруве появляется организация.

Здесь есть неочевидный момент: считать ли `OrganizationApplication` просто журналом заявок или агрегатом, который переводится в итоговую `Organization`.

## Decision

Вводим:

- `User` c ролью `USER` или `ADMIN`
- `OrganizationApplication` со статусами `PENDING`, `APPROVED`, `REJECTED`

И фиксируем правило:

- `approve` выполняется через отдельный use case;
- этот use case одновременно:
  - проверяет, что reviewer имеет роль `ADMIN`;
  - создает `Organization`;
  - переводит заявку в `APPROVED`;
  - сохраняет `organizationId` внутри заявки.

## Consequences

Плюсы:

- бизнес-флоу из продукта выражен напрямую в модели;
- заявка становится трассируемым источником происхождения организации;
- следующий шаг с membership можно навешивать поверх уже завершенного approval flow.

Минусы:

- создание организации и смена статуса заявки пока не атомарны на persistence уровне, потому что проект in-memory;
- при переходе на production persistence потребуется транзакционная граница.

## Next Step

Следом нужно вводить:

1. membership пользователя в организации;
2. привязку `Venue` и `Event` к `Organization`;
3. read-model заявок для админской модерации.
