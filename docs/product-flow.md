# Product Flow

## Goal

Собрать единый документ, который описывает реальный целевой сценарий платформы:

1. Есть пользователи.
2. Есть админы.
3. Есть организации.
4. Пользователь подает заявку на создание организации.
5. Админ видит заявку и аппрувит или отклоняет.
6. После аппрува пользователю создается доступ к организации.
7. Далее представитель организации создает venue, space, структуру/шаблон рассадки.
8. Затем создает мероприятие и присваивает ему категорию.
9. Конечный пользователь получает список мероприятий в своем городе, может фильтровать по категории и открывать карточку мероприятия.
10. Затем покупает билет.

## Main Actors

- `User` - конечный пользователь платформы.
- `OrganizationManager` - пользователь, который управляет своей организацией и ее мероприятиями.
- `Admin` - оператор платформы, который модерирует заявки на организацию.
- `Organization` - сущность владельца площадок и мероприятий.

## Main Business Flow

### 1. Регистрация и доступ

1. Пользователь создает обычный аккаунт.
2. Пользователь подает заявку на создание организации.
3. В заявке указываются базовые данные организации.
4. Админ просматривает список заявок.
5. Админ аппрувит или отклоняет заявку.
6. Если заявка аппрувнута:
   - создается организация;
   - пользователь становится менеджером организации;
   - пользователю отправляются данные доступа или подтверждение прав.

### 2. Подготовка каталога

1. Менеджер организации создает `Venue`.
2. Внутри `Venue` создает один или несколько `VenueSpace`.
3. Для пространства создает структуру площадки:
   - либо шаблон рассадки;
   - либо сценарий без рассадки.
4. Создает или выбирает `Category`.
5. Создает `Event`, привязывает его к `Venue`, `VenueSpace` и `Category`.

### 3. Публикация и поиск

1. Пользователь открывает список мероприятий.
2. Фильтрует по городу.
3. Фильтрует по категории.
4. Получает карточки мероприятий.
5. Открывает конкретное мероприятие.

### 4. Покупка без рассадки

Сценарий: концерт, стендап, open-air, танцпол и т.п.

1. Организация задает максимальное число билетов на событие или по типам билетов.
2. Пользователь выбирает тип билета и количество.
3. Система проверяет остаток.
4. Система создает заявку в платежке.
5. На время оплаты нужное количество билетов резервируется.
6. Если платеж успешен:
   - резерв превращается в продажу;
   - пользователю выдается билет.
7. Если платеж неуспешен или истек таймаут:
   - резерв снимается;
   - билеты снова становятся доступными.

### 5. Покупка с рассадкой

Сценарий: театр, кино, концертный зал, арена.

1. Пользователь открывает схему мест.
2. Видит только доступные места.
3. Выбирает конкретные места.
4. Система ставит выбранные места в hold до завершения оплаты.
5. После создания заявки в платежке эти места больше нельзя выбрать другим пользователям.
6. Если платеж успешен:
   - hold переводится в sold;
   - пользователю выдается билет на конкретные места.
7. Если платеж неуспешен или истек таймаут:
   - hold снимается;
   - места снова переходят в available.

## Concurrency Rules

Для бронирования и покупки нужно зафиксировать строгие правила конкурентного доступа.

### General Admission

- Нельзя продавать больше билетов, чем задано организацией.
- Пока платеж не завершен, нужное количество билетов должно быть в hold.
- Повторная продажа тех же единиц емкости недопустима.

### Seated

- После создания платежной заявки место должно стать недоступным для выбора другими пользователями.
- Одно и то же место не может одновременно находиться в двух активных оплатах.
- При неуспешной оплате место обязано вернуться в `AVAILABLE`.

### Implementation Note

Для этого слоя понадобится защита от гонок:

- либо синхронизация на уровне приложения;
- либо lock/mutex по `eventId`;
- либо более строгая стратегия на persistence уровне;
- либо отдельный reservation service с TTL на hold.

Для in-memory режима на старте достаточно сериализовать операции по событию. Для production-перехода этого будет недостаточно без устойчивого механизма блокировок.

## Recommended Delivery Order

1. `User`, `Admin`, базовые роли и организация.
2. Заявка на организацию и admin approval flow.
3. Membership пользователя в организации.
4. Venue / VenueSpace / LayoutTemplate оставить как есть и привязать к организации.
5. Event привязать к организации.
6. Read API для списка мероприятий по городу и категории.
7. General admission purchase flow с hold и подтверждением оплаты.
8. Seated purchase flow с жестким hold на время оплаты.
9. Ticket issuance.
10. Notifications.
